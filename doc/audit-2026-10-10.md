# Project audit — 2026-10-10

Reviewed commit `c4347dd`, with an initially clean worktree. This report is the only tracked change made by the audit. Findings are ordered by practical impact. P2 means a correctness or reliability problem to fix; P3 means a lower-impact UI defect.

## Findings

### 1. P2 — The download integration test deadlocks after the admission change

Locations: `tests/postgres_api.rs:1237–1251`, `src/media.rs:206–209`; further saturation assertions occur later in the same test.

The test holds two unconsumed download responses, exhausting both download permits. It then awaits a third response and expects `503`. The current handler awaits `acquire_owned()`, so the third request cannot return until one of those first two responses is consumed or dropped. The test only releases a response after that await. There is no timeout around this cycle, and the response-body path has no deadline, so the database test suite can hang indefinitely.

This is established by the ownership and control flow in the source; the PostgreSQL suite could not run in this environment. The upload admission test already tests waiting instead of rejection. `doc/todo.md` explicitly records the decision to wait, so waiting itself is intentional. The download test and the saturation sections of `doc/protocol.md` and `doc/request-limits.md` were not updated to match that decision.

Fix: spawn the third request, assert it remains pending, consume or drop one held response, then assert the queued request succeeds. Bound the test's waits so a regression fails instead of hanging. Update the protocol and request-limit documentation to describe the implemented queue behavior.

### 2. P2 — Immediate context-menu uploads discard failed work

Location: `client/src/extension/background.js:37–75`.

Only tagged or locked-session uploads receive an individual ID and a persisted `upload:<id>` source. When the library is already unlocked, the default context-menu action sends directly from a temporary object. If fetching, encrypting, or uploading fails, the catch block sends a notification and the session is disposed. No pending item or retry UI remains. The user must find the original media and initiate the upload again; the source can have disappeared by then.

This violates the project convention that pending context-menu uploads have individual IDs and remain available after failures.

Reproduction: invoke the real background handler with an unlocked identity, a successful small media fetch, and an API response of `503`. Observed zero pending-source storage writes and only a `service unavailable` notification.

Fix: persist every context-menu source under an individual ID before starting work. Clear it only after successful upload, and expose failure through a retryable pending workflow. Treat notification failure after a successful upload separately from transfer failure.

### 3. P2 — Cancellation does not reach media fetched inside a tab

Location: `client/src/extension/fetch-media.js:30–64`.

`fetchInTab()` checks the caller's signal before and after `executeScript()`, but the injected function owns a separate `fetch()` and reader with no cancellation channel. Aborting preparation or changing the library cannot stop that fetch or settle the pending script call. A stalled stream can run indefinitely, and the tab retains accumulated chunks until it completes, fails, or reaches the byte limit. This affects blob URLs and authenticated media that use the tab fallback.

Reproduction: execute the actual injected function through a scripting stub with a stalled `ReadableStream`, then abort the caller. Observed `aborted=true`, `tabFetchCancelled=false`, and `promiseSettled=false`. Closing the stream eventually produced `AbortError`; cancellation was checked only after the work completed.

Fix: give injected reads their own request IDs and abort controllers, and propagate cancellation to the owning frame through a message or follow-up injection. Also bound injected fetch/read duration and clean up readers and retained chunks on every exit. A race that merely rejects the outer promise would leave the underlying read running.

### 4. P2 — A lost registration response permanently strands the invitation and identity

Locations: `client/src/lib/stores/session.js:134–149`, `src/db.rs` invitation consumption; coverage gap at `client/e2e/settings.spec.js:265–305`.

Creation generates a fresh identity and retains it only inside the current action. The server atomically consumes the invitation and registers the public key. If that commit succeeds but the response is lost, the client catches a network error before saving the wrapped identity. A retry generates a different key, and the already-consumed invitation fails. The registered key has become unusable, and the user needs another invitation from the administrator. A local persistence failure after successful registration has a similar consequence when the wrapped identity was not saved.

Reproduction: simulate a successful server-side registration followed by a dropped response, then retry creation with the same invitation. Both attempts returned false, no wrapped identity was stored, and the retry used a different public key. The current E2E lost-response test confirms that no identity is saved but does not test successful recovery from the committed registration.

Fix: retain an encrypted pending creation identity separately from the configured library, reuse it across retries, and reconcile ambiguous registration outcomes with a signed request using that identity or an idempotent server registration mechanism. An uncertain outcome should not instruct the user to retry creation with a new key and the spent invitation. Cover lost responses and local storage failures after commit.

### 5. P2 — A transient preparation failure leaves the upload popup unable to retry

Locations: `client/src/lib/stores/pending-upload.js:74–106`, `client/src/lib/views/Upload.svelte` submit-button availability.

Source preparation runs once when the pending store is created. If fetching the source fails, the store sets an error but leaves `source` unset and `available=false`. The upload button stays disabled, and `send()` immediately returns without preparing again. The session entry is retained, but the existing popup cannot recover after the network returns. Upload-stage retries work; preparation-stage retries do not.

Reproduction: make `prepareMedia()` throw a temporary fetch error, wait for readiness, and call `send()`. Preparation ran once, availability remained false, and no second attempt occurred.

Fix: expose a preparation retry action, or let explicit submission rerun preparation when the persisted source exists. Keep preparation errors distinct from “nothing to upload,” and test recovery in the same popup without reloading it.

### 6. P3 — Downloading an image without a thumbnail renders an empty preview

Location: `client/src/lib/components/MediaCard.svelte:15–23`; `client/src/lib/stores/media-item.js` content/download state.

When an image has no optional thumbnail, its card initially shows “Open image.” Downloading it populates `$media.url` while leaving `$media.shown=false`. The image branch becomes active because the URL exists, but its `src` selects `$media.preview`, which is empty. Firefox displays a blank preview with the filename instead of the available image.

Reproduction: use a valid encrypted PNG item with no thumbnail, click Download, and inspect the card. The image's `src` attribute was `""`. Confirmed in an actual Firefox screenshot at `client/e2e/shots/audit-missing-preview-after-download.png`.

Fix: use the decrypted URL when no thumbnail exists, such as choosing the URL when `shown || !preview`. Add a browser regression case for Download before Open on an image whose thumbnail was omitted.

## Existing risks and scope limits

The repository already documents these gaps; they remain relevant to operating the current implementation:

1. **Unbounded transfer waiting and shutdown.** Download responses hold one of two slots until drained or disposed. There is no response-duration limit, semaphore-wait deadline, or overall shutdown deadline. Two stalled downloads can indefinitely block other downloads and graceful shutdown. Upload body deadlines start after acquiring a permit, so they do not bound queue time. Preserve the requested waiting behavior while defining finite wait/response limits or an enforced proxy policy.
2. **Storage and abuse controls.** There are no per-owner storage quotas or built-in request-rate limits. Registration is unauthenticated and reads a bounded body; knowing a registered public key can trigger the allow-list lookup even with an invalid signature. Deployment depends on the documented private database and reverse-proxy abuse controls. The external `i2nfra` repository and live proxy configuration were unavailable to this audit.
3. **Whole-file buffering.** Uploads and downloads retain complete bounded ciphertext buffers, with additional client and SQLx allocations. Transfer slots limit active large workflows but do not create a hard process-memory bound or bound queued HTTP connections. Existing profiling results were reviewed, not reproduced.
4. **Threat-model exclusions.** The design does not detect every server rollback or omitted search result, and immutable cached ciphertext may remain readable after deletion. Fresh encryption on an ambiguous upload retry may create a second item; that behavior is explicitly documented. No formal cryptographic proof or external penetration test was performed.

Fix the download test and its documentation first so PostgreSQL verification can complete. Then prioritize durable upload retry and recoverable creation, followed by tab-fetch cancellation and preparation retry. Production code was not changed by this audit.
