# Project audit — 2026-10-22

Reviewed snapshot: `36e26a9` on `block_model`.

This note records findings from a full audit of crypto risks, simplification,
usability and refactoring opportunities. It does not itself authorize changes;
each item in the execution order receives its own change specification before
implementation. Reassess findings against the current code when preparing a spec.

Scope reviewed: `src/` (auth, routes, chain, db, blobs, permits, pairing, web),
`sql/001_init.sql`, client `protocol/`, `services/` (library-identity, files,
library-api), `stores/` (chain, session, uploads, library, materialized-view),
the views (Setup, Unlock, Settings, Library) and components, the extension bridge,
and `doc/protocol.md` + `doc/shared-seed/`.

Overall verdict: the cryptographic core is sound. Strict Ed25519 with weak-key
rejection, canonical MessagePack re-encoding checks everywhere, domain-separated
sign/hash/AAD strings, per-block HKDF salts, random per-file and per-object keys,
positional chunk nonces under a fresh key per file (no nonce-reuse path found:
each chunk index is encrypted once, and a restart uses a new key), chunk hash plus
AAD checked before plaintext is exposed, nonce consumed before the body is read,
and atomic registration. The real risks are at the edges: the browser execution
environment, transport policy, and availability.

## A. Crypto / security findings

| # | Sev | Finding | Where |
|---|-----|---------|-------|
| A1 | **High** | **No script CSP.** HTML responses set only `frame-ancestors 'none'`. Any XSS or injected script gets full library authority. It can sign blocks with the non-extractable key, and it can call `sealLibraryBackup` to export the seed under a password it picks. The library-identity boundary doesn't protect against same-origin code (the docs say so), so CSP is the main defense. Add `default-src 'self'; script-src 'self'; worker-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'; img-src 'self' blob: data:; media-src 'self' blob:; connect-src 'self' https: http://localhost:* http://127.0.0.1:*` plus `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`. First check that the Vite build emits no inline scripts or styles (Svelte puts component CSS in the bundle, so `style-src 'self'` should work). | `src/web.rs` `html_response` |
| A2 | Med | **Plain-HTTP servers are accepted for any host.** `checkServer` allows `http:` everywhere. Credentials name the origin, and every request and every block travels over that channel. A network attacker on plain HTTP can't forge requests, but it can read metadata and the access pattern, and withhold or replay pages. Require `https:` except for loopback, the same rule the extension already uses. | `client/src/lib/protocol/server.ts` |
| A3 | Med | **Weak master-password policy.** The only rule is `minlength=8`. The local seal uses PBKDF2 with 600k iterations, so an 8-character password from a stolen IndexedDB profile is crackable offline, and it yields the permanent, unrevocable seed. Add a strength meter or a passphrase suggestion. Optionally move the local wrap to a memory-hard KDF; that's a format change, so it needs its own decision. | `views/Unlock.svelte`, `protocol/password.ts` |
| A4 | Med (design) | **One permanent seed and no revocation** (accepted in the spec). A lost device holding the seed has permanent full authority. The UI never says this, and no "move to a new library" path exists. At minimum, explain it in Settings → Forget/backup. Rotation is out of scope without an explicit requirement. | Settings copy |
| A5 | Low | The backup password is 256-bit random but still goes through PBKDF2 with 600k iterations (several seconds on mobile, for no security gain). HKDF would be enough. This changes the format, so batch it with any other backup-format change. | `library-identity.ts` `sealBackup` |
| A6 | Low | The pairing join limit (120/min worldwide) and the first-joiner-wins rule let one IP range block all pairing, or squat a known room ID. OPAQUE plus the 40-bit secret plus the SAS still keeps credentials safe. Possible fix: per-room join-attempt cap; keep the global cap. | `src/pairing.rs` |
| A7 | Low | The extension fetches any http(s) URL it is given, including intranet/RFC1918 hosts. Low impact because only right-clicked media is fetched, without credentials. Optionally reject private-address hosts. | `client/extension/capture.ts` |
| A8 | Info | Freshness and withholding by the server, and poisoning by an authorized writer, are documented and accepted. Delivering the client code from the server means a malicious server can serve malicious JS. That's inherent to web crypto; the extension is the only mitigation. Mention it in `doc/protocol.md`'s threat model. | docs |

## B. Reliability / correctness (user-visible)

| # | Sev | Finding | Where |
|---|-----|---------|-------|
| B1 | **High** | **Uploads are lost whenever the head moves during an upload.** `uploads.ts` captures `expected` before preparation and encryption. `FilesImpl.uploadFile` checks it again at start, and `ChainStore.appendMutation` rejects a mismatch at commit. A tag edit, delete, or another device's upload during a long upload throws away every staged chunk ("The library changed. Select the file again"). `AddFile` doesn't depend on prior state (only on a fresh ID), so it should rebase onto the current head at commit. Same for Delete/Restore/Purge when the file's lifecycle state still allows the change. Only `ReplaceMetadata` needs optimistic revision checking, which `prepareMetadata` already does by comparing the metadata hash. | `stores/uploads.ts:187`, `services/files.ts` `uploadFile`, `stores/chain.ts` `appendMutation` |
| B2 | Med | The global `mutating` flag rejects any second mutation ("already in progress"). A tag edit made while an upload is committing fails outright. Queue mutations through a single serialized promise chain instead. Deliberate rejection was meant for *overlapping edits of the same item*, not unrelated ones. | `stores/chain.ts` |
| B3 | Med | Every tab start fetches every file's metadata blob one request at a time (`materialized-view.ts:228`), with a 2-download per-key server limit. At the 10,000-file quota that's minutes of "Loading metadata…". Option 1: fetch with bounded concurrency (2, matching the server). Option 2 (needs a decision because it adds persistence): cache the immutable, hash-addressed encrypted metadata blobs in the existing IndexedDB chain storage. | `stores/materialized-view.ts` |
| B4 | Low | The quota pre-check is duplicated in `uploads.ts` and `files.ts`, with slightly different logic (compression exemption). Keep one owner. | same |

## C. UI / usability (average user)

1. **Block-number history selector sits at the top of every Library page**
   (`HistorySelector.svelte`: "Block", "Browse block", "Live view · block N"). It's
   blockchain jargon shown first to every user. Move it into a collapsed
   "Browse earlier versions" disclosure, or into Settings, and say "version" instead of "block".
2. **Onboarding has too many steps and asks for things in the wrong order.** Today: master password → Create → *Prepare
   library* → prepare backup → download → copy password → *then* invitation code →
   Create. Proposed: one Create form asking for the invitation code up front, then a single
   "Save your recovery kit" step (download, then show/copy the password with a "I saved it" checkbox), then
   done. Keep the existing rule that registration happens only after the download.
3. **The no-match search state has no "Clear search" button.** AGENTS.md requires one
   (`Library.svelte` empty branch).
4. **Jargon in Settings and Setup**: "Encrypted history", "trusted head", "rollback
   protection", "Retained files", "staged uploads". Rewrite in plain words, e.g. "Storage used",
   "Files", "Forget this browser: you'll need your recovery kit or another
   device to reconnect".
5. **Settings layout**: make every section collapsible, with only "Your library" open (already in
   `doc/#todo.md#`). The `$session.notice` paragraph sits between sections, away from its
   action, which breaks the "status beside action" convention.
6. **Upload is disabled while an upload is running.** Let new selections join the
   in-memory batch queue (the batch is already sequential).
7. **"Refresh" is the only way to see other devices' changes.** Polling isn't allowed, but
   syncing on `visibilitychange` is cheap. AGENTS.md also forbids focus checks, so this
   needs an explicit decision; excluded until then.
8. The backup password is a 43-character base64url string. Show it grouped (e.g.
   `xxxx-xxxx-…`) and accept it with or without separators.
9. Upload preview compaction and showing the converted file extension (from `#todo.md#`).

## D. Simplification / refactoring

1. **Documentation sprawl**: 67 files in `doc/`. Several describe removed designs
   (`device-preserving-rotation.md`, `genesis-and-recovery-enrollment.md`,
   `library-recovery.md`, the device sections of `blockchain-storage.md`,
   `branch-review-2026-10-21.md`, which names deleted modules) and `priorities.md` (talks about
   per-key quotas and owners). Delete superseded specs (git keeps them),
   fold what still applies from `blockchain-storage.md` into `protocol.md`, and keep an index in
   `doc/README.md`.
2. **Large stores**: `session.ts` (783), `pairing.ts` (723), `library.ts` (669),
   `content-streams.ts` (563). `session.ts` mixes lock/unlock, creation/registration,
   backup, and restore. Pull the backup and creation workflow out into its own store class, owned by
   the session. Review `pairing.ts` for duplicated sender/receiver state machines.
3. **Small duplicates in `library-identity.ts`**: local `hex()`/`equal()` duplicate
   `bytesToHex`/`sameBytes`. `checkpoint()` inlines hex again. The `identities` WeakMap maps
   each object to itself; a `#disposed` check on the instance gives the same effect.
4. **Stale Rust comments**: `auth.rs` header still mentions "allow-list" and
   "endpoint-specific authority/membership". `db.rs` mentions "historical keys". `chain.rs` says
   "no membership lookup". There's a `FIXME` in `pairing.rs:room`. Change to single-library
   wording.
5. **Rust DB style**: long one-line SQL strings in `db/chain.rs` and `db/blobs.rs`
   (inconsistent with the formatted queries in `db.rs`). Reformat as raw multiline strings.
   `block_page` and `lock_library` duplicate the library SELECT, so share a helper.
6. `PurgeFiles` is plural, but the client always passes one ID (already noted in
   `priorities.md`). Make it singular. That's a protocol/vector change, so do it only alongside another format change.
7. Unify image and video compression behind one interface (`#todo.md#`).
8. Untracked editor autosave files (`doc/#todo.md#`, `doc/#settings-ui.md#`,
   `client/src/lib/media/#upload.ts#`). Their content (the todo list) should move into a tracked doc.

   Keep `ReplaceMetadata`'s revision check. Tests in `client/tests/chain-store.test.ts`

   upload both succeed; a stale metadata edit is still rejected.
