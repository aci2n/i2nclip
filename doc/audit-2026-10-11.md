# Project audit — 2026-10-11

Reviewed the clean working tree, including the previous audit fixes, Rust authentication and media handlers, PostgreSQL ownership/transactions, client API and crypto framing, session/storage adapters, library/media/tag stores, upload coordination, and packaging. Findings below describe the current source; application code was not changed.

## 1. P2 — Web reset leaves plaintext identities in other tabs

Locations: `client/src/lib/platform/web.js:45`, `client/src/lib/stores/session.js:39`, `client/src/lib/stores/session.js:232`.

The web adapter uses tab-scoped `sessionStorage` for the unlocked private key and shared `localStorage` for the encrypted identity. Reset clears only the invoking tab's session storage. Other tabs refresh after the local-storage change and stop displaying an unlocked library, but refresh never removes their persisted private keys. Closing the reset tab does not clear those other tabs' keys. Restoring the same library makes an already-open tab accept its old plaintext key again because refresh compares only the public key.

Reproduced with the actual web adapter loaded as two independent page modules, shared local storage, separate session storage, and the actual session store. After resetting page A, page B's session storage still contained `privateKey`. Reinstalling the matching encrypted identity made B's `credentials()` return the old key without unlocking again. The encrypted-identity placeholder in this controlled reproduction is sufficient because refresh does not decrypt it; a valid restored encrypted identity follows the same branch.

Fix: bind session keys to a persisted session/identity generation that reset invalidates across tabs, and erase invalid session keys when refreshing. Test reset and subsequent restoration across two real browser pages, including a suspended page that misses the reset event.

## 2. P2 — JSON and error responses bypass streamed size limits

Locations: `client/src/lib/api.js:162`, `client/src/lib/api.js:268`, `client/src/lib/api.js:301`.

Encrypted content reads enforce a streamed 32 MiB limit, but successful JSON responses use `response.json()` directly and failures use `response.text()` directly. Registration failures are affected as well. A broken API, proxy, or selected server can therefore make these paths buffer arbitrarily large responses. Error text is then retained in an Error and often in UI state; the limit cannot be enforced after parsing or decryption.

Reproduced by calling the actual `registerKey()` with a mocked fetch returning a chunked 502 response containing 34 one-MiB chunks and no Content-Length. All 35,651,584 bytes were consumed and retained in the error message. No excessive allocation was needed beyond this bounded demonstration. The same unbounded response consumers are used for list, metadata, upload acknowledgments, and metadata conflicts.

Fix: use bounded streaming readers for JSON and error bodies, with limits sized for a 24-item metadata page, one metadata item/conflict, and small acknowledgments/errors. Cancel the stream on overflow and keep displayed error text short. Cover missing/dishonest Content-Length and oversized success/error responses. XHR upload acknowledgments also need a response limit because their responseText is buffered before constructing a Response.

## 3. P2 — Transfer saturation can indefinitely block other libraries and shutdown (known open issue)

Locations: `src/media.rs:175`, `src/media.rs:207`, `src/media.rs:309`, `src/lib.rs:201`.

Upload and download admission wait on shared semaphores without deadlines. Download bodies retain their permits and complete ciphertext buffers until drained or dropped. A registered client with sufficiently large files can occupy all sixteen download slots with slow receivers and keep other owners' content requests queued indefinitely. Slow-body uploads can likewise keep the four upload slots occupied, with queued uploads outside the body-read timeout. Graceful shutdown has no overall deadline and does not close admission; active transfers can delay termination until the container runtime kills the process.

This is already accurately documented in `doc/request-limits.md` and proposed for correction in `doc/transfer-shutdown-proposal.md`; it is not a regression introduced by the recent fixes. Existing controlled body/permit and admission tests verify retention and queued-request behavior. Actual production proxy timeout behavior was not inspected, so deployment-level mitigation is unknown.

Fix: implement finite admission waits, response-drain/transfer deadlines, and a bounded shutdown sequence. Verify with slow receivers and queued requests across owners.

## Follow-up — Finding 1 fixed

Reset clears the shared library identity first. Each open web tab receives the
`localStorage` event, rereads the identity, and removes its own tab-scoped
session key. Web tabs also recheck storage on focus, visibility return, and
`pageshow`. A per-identity generation binds each unlocked session to the
identity it unlocked, so a tab that misses reset and restore events rejects its
old key when it resumes. Firefox extension pages use the same generation
check; their shared session storage is cleared through `storage.onChanged`.
The generation is internal browser state and does not change recovery files or
the server protocol. Existing unlocked sessions relock once on upgrade; their
encrypted identities still unlock and migrate after password entry.

The previous-source Firefox reproduction confirmed that the second tab retained
its key and unlocked after restoring the same library. The new Firefox tests
cover live and missed events, and unit tests cover concurrent refresh/unlock,
legacy migration, cleanup failure, and missing Web Locks.

All 75 Firefox tests passed after this fix, including the two reset cases and
extension legacy-session migration. `make test`, `make lint`, and `make extension`
passed. The pre-fix behavior was reproduced against an isolated Firefox build
from the original source.
